一、架构结论

当前后端不是“代码失控”，而是一个功能已经完整、边界意识已经形成，但 Hub 内部逐渐成为多能力聚合点的模块化单体。

25Go package，包含 4 个命令入口
280Go 文件，其中 80 个测试文件
PASSgo test ./... -count=1
ACTIONgo vet ./... 存在现有告警
一句话判断：保留当前进程与部署边界，先把 Hub 的“连接、路由、业务编排、任务、状态、持久化”拆成清晰的包边界；等依赖方向稳定后，再考虑独立进程或服务化。
已经做对的事 Registry/ACP 协议集中在 internal/protocol；Session、AgentInstance、AgentConn、SessionRecorder 已有明确概念；App-only Session 和 Hub-owned runtime 已形成稳定约束。
现在最值得治理的事 internal/hub/reporter.go 同时承担长连接、请求分发、项目 FS/Git、HubState、工具任务、Usage、Terminal、Relay 和配置运行时，是首要变化放大器。
暂时不要做的事 不要先升协议版本、删除兼容 schema、整体改名或直接拆微服务。先建立边界、契约测试、可观测指标和恢复不变量。

四、架构判断：优点与风险

当前值得保留的设计

契约集中

internal/protocol 集中定义 envelope、role、route、method descriptor 和 session model；Registry 2.7 的兼容边界有测试保护。

Session/Agent 分层

Session 只通过 agent.Instance 操作 ACP；AgentConn 隐藏 transport policy，provider 适配没有直接暴露给 Registry。

事件出口单一

SessionRecorder 统一记录和发布 session view，能减少多路写入导致的 transcript 与 UI 投影分叉。

运行时边界清楚

Hub-owned AgentFactory、lazy AgentInstance、shared/owned connection 和 App-only Session 已形成可演进的运行模型。

测试覆盖面广

当前有 80 个测试文件，完整 go test ./... 通过，说明行为契约和回归意识较强。

协议删除有护栏

旧方法、旧路由和 cmd.* 公共暴露有显式测试，不应把“保留的拒绝逻辑”误判为废弃实现。

主要结构性风险

风险证据影响判断
Reporter 变成 Hub 内部总线 reporter.go 约 3,665 行；同时持有 WS、pending request、session handler、tool locks、file index、HubState、usage、terminal、relay、config、bridge。 任何新功能都容易修改同一文件；并发、错误和生命周期策略相互耦合。 高影响 / 高概率
Hub 依赖方向没有自动护栏 internal/hub 直接连接 agent、client、terminal、tools、usage、protocol、security、flickerbridge、portrelay 等多个域。 抽取功能时容易反向依赖；模块名称变了，架构耦合仍然存在。 高影响 / 高概率
Session 域与持久化/投影耦合 Session 同时持有 Agent runtime、Store、view sink、queue、goal、permission；Client 又创建 Recorder、archive、search、attachment。 恢复、归档、事件重放、并发写入和 provider 切换的测试成本持续上升。 高影响 / 中概率
多种存储形态缺少统一持久化门面 SQLite 保存摘要/偏好；WMT2/文件保存 turn、artifact、attachment；配置和运行状态另有 JSON 文件。route_bindings 仍留在 schema 中作为惰性兼容表。 事实来源、写入顺序、修复方式和迁移策略难以一眼确认。 高影响 / 中概率
内部字符串命令存在漂移风险 cmd.npm、cmd.update、cmd.skills、cmd.release 仍用于 Hub 内部工具，但公共 Registry 侧已删除类似方法。 边界误读、拼写漂移、角色校验和工具生命周期难以由编译器保护。 中影响 / 高概率
可选能力没有完全隔离 Flicker Bridge、Gateway update、Skills watcher、Usage、Terminal、Release 都通过 Reporter/Hub 回调互相连接。 单一能力启动失败、重载或退出时可能放大到 Hub 主生命周期。 中影响 / 高概率
并发与背压规则分散 Reporter、Registry peer、Session queue、Tool manager、Relay 各自维护 mutex、channel、pending 和关闭逻辑。 超时、重连、写入顺序和积压指标不统一，问题定位依赖日志拼接。 高影响 / 中概率
现有 vet 告警未归零 portrelay 存在包含 sync.Once 的结构体按值复制告警；Windows Desktop 有 unsafe.Pointer 告警。 不一定立即表现为业务故障，但会削弱并发/平台边界的可信度。 中影响 / 已发生

六、建设性架构优化意见

优先做“边界收敛”和“可验证的重构”，每一步都保持 Registry 2.7 和现有 Session 语义不变。

P0

把 Reporter 变成连接层 + Dispatcher

做法：保留 Reporter 对外 API，但内部抽出 registryConnection、requestDispatcher、sessionHandler、projectQueryHandler、hubStateHandler、toolJobHandler、terminalHandler。每个 handler 只接收已解码的 request context，不直接操作 WS。

验收：新增一个 Registry method 不再修改一个超大 switch；连接重连、业务 handler、事件发布可以分别测试。

P0

建立统一 RequestContext 与策略入口

做法：定义包含 requestId、role、hubId、projectId、sessionId、connection epoch 的内部上下文；统一做 decode、scope 校验、权限判断、超时和日志字段注入。

验收：handler 不再重复 trim/parse/role/project/hub 校验；错误能稳定映射到 INVALID_ARGUMENT、FORBIDDEN、UNAVAILABLE 等标准码。

P0

加入 package import architecture check

做法：用 go list -json ./... 或 Go 小工具检查依赖方向；把 protocol、domain、application、adapter 的规则纳入 CI。

验收：出现“Session import Registry”或“protocol import hub”时 CI 直接失败，而不是等人工 review 发现。

P0

统一错误模型和可观测字段

做法：引入内部 typed error：code、retryable、safe message、cause、domain；所有跨边界回复和后台 job 都走同一转换器。

验收：日志和 Registry error 都带 requestId、projectId、sessionId、operationId；重试与不可重试错误可被客户端区分。

P1

拆出 SessionState、SessionRuntime、SessionPersistence

做法：保留 Session 作为兼容 facade，内部逐步分成业务状态、Agent/queue 执行、持久化/投影三个组件；SessionRecorder 变为显式 projector/publisher。

验收：可以用 fake Agent 和 fake Store 单测 queue、恢复、事件顺序；provider adapter 不再参与 Session snapshot schema。

P1

统一持久化边界和事实来源

做法：明确 SessionSnapshotStore、TurnStore、ArtifactStore、ArchiveStore 的接口与写入顺序，建立 recovery/repair 检查；把 JSON 配置与 Session 数据分开建模。

验收：文档能回答每个字段的唯一事实来源、写失败后的修复动作、重启后的恢复顺序。route_bindings 只能在迁移策略完成后删除。

P1

将内部 cmd.* 改为 typed ToolCommand

做法：保留现有字符串作为 transport/compat mapping，在 Hub 内部使用 enum-like command、typed payload 和 operation state；工具 Manager 不再依赖大量字符串 switch。

验收：非法 command 在构造阶段失败；每种 job 具备 accepted/running/succeeded/failed/cancelled 状态和 operationId。

P1

收敛 Agent Provider 插件契约

做法：把 provider descriptor、runtime factory、session adapter、capability matrix、credential source 分开；Codex App Server 转换只在 adapter 目录内。

验收：新增 provider 只实现契约和 capability tests，不修改 Session、Registry 或公共协议；provider-specific 字段不进入通用 Session 数据模型。

P2

把 Registry 变成可组合的控制面内核

做法：按 peer/connection、routing、project、session、server-data、speech/tts、relay、release 分 feature handler；连接层统一处理写队列、pending、backpressure、idempotency。

验收：每个 feature 有 route descriptor、auth matrix、contract test 和明确的资源上限；terminal/relay 高流量不挤占 priority response。

P2

做可选能力故障隔离

做法：Flicker Bridge、Usage、Skills watcher、Gateway update、Release 和 Terminal 按 capability service 注册；启动失败只影响对应 section/feature，不能改变 Hub 核心可用性。

验收：每个可选服务有 Start/Stop/Health、资源所有权、超时、关闭顺序和降级快照。

P2

补齐并发、恢复和平台质量门禁

做法：为 queue、Recorder、Registry writer、Relay 做 race/背压/断线测试；修复 go vet 中的值复制锁和 unsafe pointer 告警。

验收：CI 至少执行 test、race（适用 package）、vet；监控 pending 数、队列深度、Recorder lag、Agent restart、connection epoch 和 backlog drop。

七、建议落地路线

以“小步可回滚、协议不变、每步可验证”为原则，建议按下面顺序推进。

阶段 0
基线
建立规则和指标。 固化当前 package graph、关键 Registry contract、Session recovery invariant；新增 architecture check；单独处理 portrelay 值复制和 Desktop unsafe warning。产物是可比较的重构前基线。
阶段 1
Reporter
只做内部抽取。 先抽 request context/policy，再按 session、project query、hub state、tool job、terminal 拆 handler；Reporter 继续负责连接和兼容 API。每次抽取都跑 package tests 与 protocol contract tests。
阶段 2
Session
稳定持久化端口。 将 SQLite、WMT2、artifact、archive 的实现移到 adapter；SessionRecorder 明确为 event projector；建立重启、重复事件、写失败和修复测试。
阶段 3
Agent/Jobs
插件化 provider 与后台任务。 typed ToolCommand、统一 Job state machine、provider capability matrix 和 Codex adapter isolation；新增 provider 不得触碰 Session/Registry 核心。
阶段 4
Registry
优化控制面可靠性。 拆 Registry feature handlers，统一 priority/terminal 写队列、pending limit、request idempotency、backpressure 和安全策略。只有指标证明需要时，才评估独立进程。

建议的完成标准

依赖

域层不依赖 Registry/WS/SQLite；协议层无业务反向依赖；新增功能能在 application/adapter 中落位。

行为

Registry 2.7 wire shape 不变；Session queue、Recorder 事件顺序、Agent recovery 和 App-only ownership 不变。

运维

能观测连接重连、pending、queue、Recorder、Agent、job、backpressure 和可选服务 health。

八、废弃代码清理的架构原则

“没有当前调用方”不等于“可以直接删除”。后台有协议兼容、schema 迁移、恢复数据和平台入口，清理应按证据分级。

对象当前判断建议动作
route_bindings schema生产代码不查询，但 SQLite schema 仍保留惰性兼容表先做用户数据/版本迁移验证，再通过明确 migration 删除；不能仅凭 grep 直接删表。
LegacyRegistryMethodChatSend更像“显式拒绝旧协议”的兼容护栏，不是普通死代码保留 descriptor/拒绝测试，等协议升级策略明确后再整体移除。
内部 cmd.*公共 Registry 方法已删除，但 Hub tools 仍在使用不要当作废弃代码删除；先换成 typed ToolCommand，再保留字符串映射层。
Flicker Bridge v1/v2有入口参数、生命周期和 provider 依赖，属于活跃兼容能力先用运行 telemetry 确认零使用，再做 feature flag 下线和数据清理。
Desktop/Gateway/Release command不是 Hub 核心，但分别是有效运行时/部署入口从“后台核心”架构图中分层展示，不要因为不被 Hub import 就误判为废弃。
删除前的三项证据：源码和测试无引用；协议/客户端/wiki 无调用；配置、数据库、归档和升级路径无历史数据依赖。三项都满足后，仍应先加迁移或 feature flag，再删除实现。
