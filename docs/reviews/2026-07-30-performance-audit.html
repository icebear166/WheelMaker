WheelMaker 全栈性能审查

后端 Go 守护进程（~6 万行）与前端 Workspace Web UI（~6.4 万行）的静态性能审查，聚焦流式 token 转发这条核心体验路径上的反模式与可落地的优化建议。

关于本报告的置信度：server 端目前没有任何 pprof / benchmark / metrics，前端也没有渲染计时或长任务观测。本报告所有结论来自静态代码审查——凡是"看代码就能确定的反模式"（O(N²) 拼接、每帧整树 reconcile、逐 token 全量解析等）有较高把握；但"实际卡多少"需要先补上度量基线（见 B-L1）才能量化。预期收益中的数字均为基于代码结构的估算。

执行摘要

性能瓶颈高度集中在同一条路径——流式 token 转发。这恰好是 AI 工具最关键的用户体验路径（看输出流），而前后端犯了同一个结构性错误：把"每个 token"当成了"一次全量操作"。

后端：每个 token 做了太多事

流式转发管线在持锁期间做同步注册中心 ACK 往返 + 全文复制（O(N²)）+ 多次全量序列化；SQLite 每次提交 fsync；flicker bridge 每个 token 触发 6-8 次反射序列化。

前端：一个 21k 行的巨石组件

WorkspaceApp.tsx 21308 行、约 246 个顶层 state、零 Context。流式 flush 调顶层 setChatMessages，每帧整树 reconcile，叠加 Markdown 全量重 parse、Shiki 重新高亮。

核心洞察：前后端的根因是同构的——缺少边界隔离。后端缺防抖/异步/publish-out-of-lock，前端缺组件边界/selector 切片。两端最高 ROI 的修复分别是 B-H1（流式管线去 ACK 同步）和 F-H1（抽出 <ChatSurface> 子组件）。

一、后端（Go server）

数据流：CLI 子进程 → acp.Conn（纯传输）→ AgentInstance → Session → SessionRecorder → Registry session.* 事件 → App。瓶颈全部集中在 SessionRecorder → Reporter 这段录制/发布热路径，以及 SQLite 持久化和 flicker bridge 转换层。

高
B-H1

流式转发管线：持锁同步 ACK + O(N²) 文本拼接 + 多次全量序列化

📍 session_recorder.go · reporter.go · session.go

问题

每个 agent_message_chunk 都串行经过 per-project 的 writeMu，叠加四个反模式。这是全栈最严重的瓶颈，位于最高频的 per-token 路径上。即便注册中心 RTT 仅 1–5ms，在 50 token/s 的流式输出下，每秒也有数百毫秒锁持有纯等网络；注册中心一旦变慢，整个项目所有会话的录制管线全部 stall。

代码研究

(a) O(N²) 文本累积。每个 chunk 把已累积的全文复制一遍，一条 N 字节消息分 M 个 chunk 到达时总复制量 O(N·M)：

session_recorder.go:1944-1951Go
case acp.SessionTurnMethodAgentMessage, acp.SessionTurnMethodAgentThought:
    base := existing.payload.(acp.SessionTurnTextResult)
    inc := incoming.payload.(acp.SessionTurnTextResult)
    inc.Text = base.Text + inc.Text   // 每个 chunk 都把已累积的全文复制一遍

(b) AgentMessage 没有节流。只有 AgentThought 走 60s 节流，AgentMessage（普通助手输出）直接每 chunk 发布：

session_recorder.go:1187-1197Go
func (r *SessionRecorder) publishLiveSessionTurn(turn sessionTurnMessage, updateJSON string) {
    if turn.method != acp.SessionTurnMethodAgentThought || turn.finished {
        r.publishSessionTurn(turn, updateJSON) // AgentMessage 直达，无节流
        return
    }
    // 仅 AgentThought 进入 thoughtPublish 节流 ...
}

(c) 持锁期间同步 ACK 往返。PublishProjectEvent 每个 chunk 阻塞等注册中心 ACK（最长 10s）。而 ACK 不携带任何业务有效载荷，仅 "ok"，等待毫无必要：

reporter.go:1334-1352Go
select {
case resp, ok := <-waitCh:                // 阻塞等注册中心 ACK
    ...
case <-time.After(10 * time.Second): // 每个 event 一个 10s timer
    return fmt.Errorf("registry event publish timeout")
}

(d) 每个 chunk 全量序列化 4 次：buildSessionTurnContentJSON（marshal 全文）+ json.Marshal(message) + reporter.MustRaw(payload) + writeJSON 下的 conn.WriteJSON。

修复方案

  • session.* 事件改为 fire-and-forget 或批量 ACK——注册中心侧已用 broadcastProjectEvent 广播，ACK 对业务无用。
  • 把 publish 移出 writeMu：在 addMessageTurn 只更新内存状态、释放锁后再异步发布。
  • 对 AgentMessage 引入和 AgentThought 一致的节流（或按 turn 合并 flush）。
  • mergeTurnMessage 文本累积改用 strings.Builder / []byte 增量 append，发布时再切片。

预期收益

估算：单点解决转发管线最大瓶颈——流式期锁持有从"纯等网络"降为内存操作；注册中心变慢时不再 stall 整个项目；配合文本 Builder，长回复（20KB+ 代码）的 CPU 与延迟从 O(N²) 降为线性。后端最高 ROI。
高
B-H2

flicker bridge：每个流式 token 触发 6-8 次 JSON 序列化（deepCopyJSON 风暴）

📍 flickerbridge/flicker_bridge.go · v2.go

问题

OpenAI/Anthropic 流式转发路径上，deepCopyJSON（= marshal + unmarshal）被当作"克隆原语"用在 per-token 路径，且全部打在 map[string]any（反射 + key 排序 + interface 装箱）上。一个 2000 token 的回复约产生 1 万-1.8 万次序列化遍历。

代码研究

flicker_bridge.go:2194-2204Go
func deepCopyJSON(value any) any {
    data, err := json.Marshal(value)        // 序列化 #1
    if err != nil { return value }
    var copy any
    if json.Unmarshal(data, &copy) != nil { // 反序列化 #2
        return value
    }
    return copy
}

该函数在 normalizeUpstreamChunk（每个 token 调用）里被用于 payload / usage / delta 等多处；v2 路径（v2.go:1638-1645）每个 text-delta 还会分配 2 层嵌套 map[string]any 字面量，再 json.Marshal。

修复方案

  • 定义 typed struct（openAIChunk / choice / delta、v2SSEEvent）直接字段赋值，绕过反射。
  • 移除下游不修改源 map 处的 deepCopyJSON。
  • SSE 文本 delta 的静态前缀字节预计算，只拼接 delta 文本。

预期收益

估算：砍掉绝大部分 per-token CPU 与 GC 压力。N 路并发流 × M token × ~6 次反射序列化的线性放大被消除。仅当使用 flicker bridge 模式时收益生效。
高
B-H3 ✓ 已修复 · commit 50517709

SQLiteSessionStore：缺 synchronous=NORMAL，每次提交 fsync；SaveSession 双往返

📍 sqlite_store.go

问题

(a) WAL 已开启（好），但 DSN 未设 synchronous，modernc.org/sqlite 继承默认 FULL，每次提交都 fsync WAL——Windows 上 fsync 极贵。(b) SaveSession 每次先 loadSessionByID（SELECT）再 UPSERT，两次往返 + 一次 fsync，且无事务批处理。调用方在转发路径上（prompt 起止、mark/pin/rename 等），与 B-H1 叠加时持锁期间还要叠加磁盘 fsync。

代码研究

sqlite_store.go:110Go
db, err := sql.Open("sqlite", dbPath+
    "?_pragma=foreign_keys(1)&_pragma=journal_mode(WAL)&_pragma=busy_timeout(5000)")
// 开了 WAL，但缺 _pragma=synchronous(NORMAL) → 默认 FULL，每次提交 fsync

修复方案

  • ✓ 已落地DSN 加 &_pragma=synchronous(NORMAL)（commit 50517709，NewStore 与 CheckStoreSchema 两处 DSN 同步修改）。WAL 模式下提交持久性几乎不变（仅断电可能丢最后一个事务），写延迟通常降一个数量级。
  • 把 loadSessionByID 的 merge 折进 UPSERT 的 CASE（title 字段已这么做，扩展到 created_at / session_sync_json）。
  • 对非关键写（title/info 更新）按 turn 防抖合并。

预期收益

估算：写延迟降一个数量级；每个 prompt turn 的 3-5 次 SaveSession 往返减半。
✅ 主项已落地（commit 50517709）：synchronous=NORMAL 完成，含 PRAGMA synchronous 验证测试；SaveSession 折叠 SELECT 与写防抖仍为待办。

B-M4

reporter 单一 writeMu 队头阻塞 + 每入站请求 spawn 无界 goroutine

📍 reporter.go:3009-3014,672

问题 / 代码研究

所有出站帧（terminal、session 事件、大文件 fs.read / git log 响应、ping）串行过同一 writeMu，大响应会阻塞延迟敏感的 terminal/session 帧。入站请求 go r.handleRegistryRequest(...) 无界，handler 内做 runGit / WalkDir。

修复方案

引入优先级 writer（registry 侧已拆 priorityWrites / terminalWrites，hub 侧照做）；goroutine 用有界 worker pool（registry 侧已有 64+8 worker 先例）。

预期收益

terminal/session 帧不被大响应阻塞；防止 goroutine 失控。

文件索引：git 路径冗余 Lstat；walk 回退不剪 node_modules/dist

📍 file_index.go:709,746-762,712-744

问题 / 代码研究

git 路径对每个返回文件调 os.Lstat（git ls-files 本就只返回文件，校验冗余）；walk 回退只剪 .git 和 symlink，node_modules / dist 全下钻（也违反仓库"禁止扫描 dist"约定）。非 git 项目被一棵 node_modules 放大 10-100×。

二、前端（Workspace Web UI）

核心问题是架构性的：WorkspaceApp.tsx 是一个 21308 行、约 246 个顶层 state hook、零 createContext 的巨型组件。main.tsx 虽瘦身到 32 行，但所有逻辑被塞进这块巨石。结果就是任意 state 变化都重渲染所有子树——流式 token 的 flush 调顶层 setChatMessages 时，每一帧整棵组件树都 reconcile。

仓库已有一份 2026-06-04 性能设计文档，其机械项已落地（webpack 去 runtimeChunk、SW cache-first、Shiki/Mermaid/KaTeX 内容触发、Seti 移出启动路径、Codicons 已全量改内联 SVG），但最核心的"特性边界提取"步骤几乎未做——这正是当前所有前端流式/idle 性能问题的根因。详见 落地差距表。
高
F-H1

巨型组件 + 顶层 setChatMessages 导致整树每帧 reconcile

📍 WorkspaceApp.tsx（组件体 2618-21261）

问题

流式 token 正确地先写入 ref（chatMessageStoreRef）并由 rAF 调度器 createChatRealtimeFlushScheduler 合并——这一层做得好。但 flush 最终调用的是 App 顶层的 setChatMessages(fullMessages)，于是每一帧（约 60Hz）整个 18640 行组件都 reconcile。该组件持有连接/主题/File/Git/Skills/Updates/PortRelay/Debug/Terminal/Usage/Voice 等所有关注点的约 246 个 state，且没有任何 createContext——任意 state 变化都重渲染所有子树，文件里只有 5 个 React.memo。

代码研究

rAF 合并存在，但合并后提交到了顶层 state：

WorkspaceApp.tsx:4424-4437（rAF scheduler）TSX
useEffect(() => {
  const scheduler = createChatRealtimeFlushScheduler({
    flush: runtimeKeys => {
      runtimeKeys.forEach(runtimeKey => {
        setVisibleChatMessagesForRuntimeKey(runtimeKey,
          chatMessageStoreRef.current[runtimeKey] ?? [], {...});
      });
    },
  });
  ...
});

// setVisibleChatMessagesForRuntimeKey 内部最终调用：
setChatMessages(fullMessages);  // ← 每帧触发整个 21k 行组件 reconcile

修复方案

  • 把 chatMessages 及其 rAF flush 调度下沉到一个 <ChatSurface> 子组件，App 只传选中会话 key + 提交回调。
  • 非 Chat 的 state（File/Git/Skills/Settings/Debug/Terminal/Usage/PortRelay）拆到各自特性组件，仅共享 theme / 连接 / 当前 project。
  • 这是设计文档"Component Boundary Strategy"未落地的部分。

预期收益

估算：流式期 reconcile 范围从"整棵 21k 行组件"缩到"chat 子树"。长会话/低端机/移动端上 token 绘制卡顿、滚动掉帧、生成期间交互迟滞显著缓解。前端最高 ROI。

F-H2

流式期间 Shiki 代码块逐 token 重新高亮（block 模式无缓存、无 isStreaming 闸门）

📍 code/ShikiCodeBlock.tsx · code/shikiRenderer.ts

问题

ShikiCodeBlockSmall 的高亮 effect 把 content 放进依赖数组，所以流式中每个扩展代码块的 token 都会取消并重跑 renderShikiHtml。已有的内容缓存只对 inline 模式生效，block 模式从不查缓存；props 上也没有 isStreaming / finalized 字段，没有 debounce。

代码研究

ShikiCodeBlock.tsx:438-451（effect 依赖数组）TSX
}, [
  content,            // ← 流式期每个 token 都改变 content，重跑整个高亮 effect
  language,

而 shikiRenderer.ts:377-382 的缓存分支 if (options.mode === 'inline') 把 block 模式完全排除在缓存之外。

修复方案

  • 从 message.finished 接出 isStreaming prop，为 true 时只渲染廉价 fallbackHtml，仅在 finalized 跳变时触发一次高亮。
