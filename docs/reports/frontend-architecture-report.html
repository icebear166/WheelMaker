01 / 执行摘要

执行摘要

WheelMaker 前端已经具备完整产品能力和明确的基础设施分层，但应用编排层没有同步演进，形成了“底层有边界、顶层过度集中”的结构。

当前首要问题不是重写 React，也不是替换状态库，而是把 WorkspaceApp.tsx 中已经隐含存在的领域边界真正切开。

M 实测数据 S 静态扫描 I 证据推断
01 / 优势

基础层已经成形

Registry Client → Repository → Workspace Service → Store/Persistence 的职责大体清楚；平台桥接、按需加载、CSP、虚拟列表和 IndexedDB 都已有成熟实现。

02 / 瓶颈

根组件成为系统总线

单文件占全部前端 LOC 的 30.9%，内部导入 129 个模块，并承载 290 个 state、172 个 effect/layout effect 与 271 个 callback。任何局部功能都容易扩大根渲染与回归范围。

03 / 方向

渐进迁移，不做大爆炸重构

优先封顶缓存和性能预算，再按 Chat → Preview/Terminal → Settings/Port Relay 顺序抽取 feature runtime；保留现有 Registry、持久化和 UI 组件资产。

核心判断： 结构债务集中在“应用编排与状态归属”，而不是散布在所有目录。静态依赖图没有发现相对导入环，说明现在仍处于可渐进拆分的窗口期。

架构边界判断

边界清晰的部分

  • Registry transport、协议归一化和项目服务分层。
  • IndexedDB 配额、预算、驱逐和恢复逻辑。
  • Desktop / Android / Native / PWA 平台适配。
  • Shiki、Mermaid、KaTeX、Git diff 等重功能按需加载。
  • 聊天长列表由 React Virtuoso 虚拟化。

边界模糊的部分

  • WorkspaceApp 同时承担状态容器、事件路由、命令协调与页面组合。
  • feature 目录拥有视图，却未完整拥有自己的 runtime/store。
  • RegistryRepository 与 RegistryWorkspaceService 方法面高度平行。
  • 全局 CSS 体量大，feature 所有权依赖命名约定而非模块边界。
  • 部分运行时 Map 缓存与持久化预算之间没有统一资源策略。

06 / 数据流

状态、数据与事件流

系统同时存在命令流、Registry 事件流、UI 本地状态和持久化缓存。性能与一致性问题主要发生在这些流在根组件交汇的位置。

用户命令流

功能界面
用户动作：发送 prompt、打开文件、查看 diff、启动终端或更新设置。
应用编排
编排与取上下文：读取当前 project/session，更新 optimistic UI 或 loading 状态。
领域服务
项目语境封装：RegistryWorkspaceService 把通用操作绑定到当前项目。
协议仓库
协议归一化：构造方法、参数并将响应转为前端类型。
客户端 / WS
传输：RegistryClient 发出 request，经 WebSocket 到 Registry/Hub。

消息接收与流式刷新

REGISTRY 事件
session.message / update 到达 RegistryClient 的事件入口。
事件路由
当前主要在 WorkspaceApp 识别 project/session、修复 gap、同步状态，并写入运行时 Map/Ref。
增量模型
最近优化改为增量 upsert turn、prompt 状态索引，避免每个 token 重扫整个会话。
逐帧提交
同一帧内的流式事件合并为一次 UI commit；空闲时不保留常驻 requestAnimationFrame。
虚拟列表
React Virtuoso 只渲染视窗附近 turn；display height 使用 WeakMap 缓存，旧消息可被 GC。
近期性能优化基线： 在 4,303 turns / 269 prompts 的长会话样本上，旧 prompt 扫描微基准约 1,723 ms；冷索引展示约 111 ms，热路径约 20 ms，单次增量 upsert 约 0.017 ms。该结果证明“索引 + 增量更新 + 帧合并”方向有效，但仍需浏览器内 Performance trace 作为持续门禁。

  • 源文本读取与 toContain 让重命名、抽取模块产生大面积无行为变化的失败。

10 / 迭代路线

分阶段迭代建议

路线以“先建立资源边界，再迁移状态所有权，最后收敛基础设施”为顺序。每阶段都可以独立交付，不需要停摆式重构。

第 0–2 周

封顶风险与建立门禁

  • Registry debug 设 1,000 条 / 8 MB 双上限，改为面板局部订阅。
  • Chat runtime Map 引入会话 LRU 与 32 MB 硬上限。
  • archive/delete 清理 messages、turns、cursor、height/index。
  • 固化 5k turns 输入与 streaming 基准。
  • 修正 releasePublish 测试漂移。
第 2–6 周

抽出 Chat Runtime

  • 建立 chat/runtime：store、event reducer、commands、selectors。
  • Registry session 事件先进入 domain router，再通知视图。
  • 使用 useSyncExternalStore 或等价局部订阅控制更新扇出。
  • 保持 composer 状态在输入边界内，不上收根组件。
  • WorkspaceApp 降到 <8k LOC、<120 state、<80 effects。
第 6–12 周

按工作台迁移所有权

  • PreviewRuntime 接管 tab/loader/navigation；TerminalRuntime 接管会话生命周期。
  • Settings、Port Relay、Voice 分别拥有异步任务与轮询。
  • Registry methods 按 session/project/git/ops 切片。
  • CSS 建 tokens/components/features layers。
  • WorkspaceApp 降到 <3k LOC、<40 state、<25 effects。
第 12 周以后

收敛目标架构

  • App 只做 Provider、路由与 ResponsiveShell 组合。
  • 每个 feature 通过 public API 暴露 Surface + Runtime。
  • 所有缓存具备条目/字节/生命周期策略。
  • 入口 JS ≤1.5 MiB、CSS ≤250 KiB（未压缩 minified）。
  • 源码字符串测试减少 50% 以上，关键流有集成契约。

11 / 目标架构

建议目标架构

目标不是追求目录漂亮，而是让一次 session.message 只唤醒 ChatRuntime 和当前可见 turn，让一次 Port Relay 轮询只影响 Port Relay，让 App 不再知道领域细节。

web/src/ ├─ app/ │ ├─ App.tsx # providers + route composition only │ ├─ AppRuntime.ts # start/stop domain runtimes │ └─ eventRouter.ts # registry event → domain runtime ├─ shell/ │ ├─ ResponsiveShell.tsx │ └─ navigation/ ├─ features/ │ ├─ chat/ │ │ ├─ public.ts # only exported contract │ │ ├─ ChatSurface.tsx │ │ ├─ runtime/ # store, reducer, commands, selectors │ │ ├─ composer/ │ │ └─ turns/ │ ├─ files/ │ ├─ git/ │ ├─ preview/ │ ├─ terminal/ │ ├─ settings/ │ └─ port-relay/ ├─ domain/ │ ├─ project/ │ ├─ session/ │ └─ workspace/ ├─ infrastructure/ │ ├─ registry/ │ │ ├─ transport/ │ │ ├─ session/ │ │ ├─ project/ │ │ ├─ git/ │ │ └─ operations/ │ ├─ persistence/ │ └─ platform/ └─ styles/ ├─ tokens.css ├─ reset.css ├─ components/ └─ features/

三条架构决策

1. Feature 拥有运行时

目录不只放组件。每个工作台拥有事件 reducer、commands、selectors 与清理策略，通过 public API 对外。

2. 事件先路由再渲染

Registry 事件进入薄 eventRouter，按 domain 分发；根组件不解析 session.message 的业务细节。

3. Store 选择服从订阅粒度

优先复用 React 与 useSyncExternalStore；只有当跨域事务或调试需求证明必要时，再引入第三方状态库。

4. 缓存都是产品能力

每个缓存必须说明 key、所有者、条目上限、字节上限、淘汰策略、清理时机和可观测指标。

5. 保留现有基础设施

RegistryClient、Persistence、平台桥和重依赖 lazy loading 是可复用资产；以接口包裹，不做同步重写。

6. 测试跟随公共契约

测试 public API、用户行为和存储/事件契约，避免检查内部文件是否包含某一行源码。

建议迁移切片

按依赖与收益排序的迁移顺序
顺序切片为什么先做完成定义

12 / 领域词汇

项目领域词汇

统一术语有助于后续拆分时避免把协议对象、UI 状态和运行时缓存混为一谈。

Registry
前端连接的协议入口，负责请求/响应和事件分发；不是 React 状态库。
Hub
Registry 暴露的整体运行状态与协调语境，前端可读取 hub state。
Project
工作空间的顶层领域对象，为文件、Git、Session、Terminal 提供共同作用域。
Session
一次持续对话及其状态、配置、附件、消息、归档和恢复生命周期。
Turn
聊天时间线的渲染/组织单元，可包含用户输入、模型内容、函数调用、计划和 diff。
Prompt
用户向 Session 提交的一次输入；可由文本、富文本、附件或选项回复构成。
Artifact
Session 产生的可独立读取或预览的产物。
Preview
文件、prompt diff、附件、Port Relay 等内容共享的多标签查看工作台。
Workspace
前端对当前 Project、Session、导航、缓存和恢复流程的应用级组合语境。
Port Relay
把远端或本地服务目标映射成前端可打开 URL/Frame 的代理能力。
Runtime Store
应用运行期内存状态；应与跨启动的 IndexedDB Persistence 明确区分。
Gap Repair
事件丢失、游标不连续或恢复后，通过重新读取补齐 Session 状态的机制。
