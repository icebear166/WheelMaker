# Android Response Image Share Design

## Goal

Change the response image export action so APK users share the generated response PNG through the Android system sharesheet, while PWA and WheelMaker Desktop users keep the current PNG download behavior.

This applies only to the camera button shown on completed response separators. The chat composer attachment tray `Photo` action keeps its current image attachment behavior.

## Context

The current response image export flow renders the selected response Markdown into a hidden export surface, captures that surface with `html-to-image`, then downloads the PNG through a `blob:` object URL.

That browser download path works for PWA and WheelMaker Desktop. It is broken in the Android APK because `MainActivity.enqueueDownload()` only accepts `http://` and `https://` URLs, so WebView rejects the `blob:` URL generated by `downloadBlobAsFile()`.

The APK flow should not rely on blob download fallback. Android needs a native sharing bridge for generated response images.

## Decisions

- The source action is the completed response camera/export button.
- The exported image content stays identical to the current downloaded PNG.
- PWA and WheelMaker Desktop continue to download the PNG.
- APK uses Android native sharing when the image share bridge is available.
- APK does not attach extra text to the share payload.
- APK uses only a temporary app cache file for `FileProvider` sharing.
- APK does not save the image to Downloads, Photos, MediaStore, or any other user-visible local location.
- If the Android share bridge is missing, the Web UI shows an update-required error instead of attempting blob download.
- If Android sharing fails, the Web UI shows an error and does not save the image locally.
- The export/share action is busy while a PNG is being generated or handed to Android, preventing repeated clicks.

## Architecture

### Web

The existing `MarkdownImageExportSurface` remains the renderer. It receives Markdown content, waits for async renderers and images, then calls `renderMarkdownElementToPngBlob()`.

After the blob is produced, Web dispatches it through a platform-aware response image output service:

- Browser/PWA/Desktop: call `downloadBlobAsFile(blob, fileName)`.
- Android APK with `WheelMakerAndroidNative.shareResponseImage`: convert the blob to a `data:image/png;base64,...` URL and call the native bridge.
- Android APK without the bridge: report an update-required error.

Android host detection should use the existing `WheelMakerAndroidNative` signal. The share capability check must require the specific `shareResponseImage` method so older APKs fail with a clear update message.

### Android

Add an `AndroidImageShareRuntime` owned by `MainActivity` and exposed through `WheelMakerBridge`.

The bridge method shape is:

```kotlin
@JavascriptInterface
fun shareResponseImage(rawJson: String): String
```

The request JSON contains:

```json
{
  "fileName": "wheelmaker-response-turn-7-2026-05-23T10-11-12-345Z.png",
  "dataUrl": "data:image/png;base64,..."
}
```

The response JSON contains:

```json
{
  "ok": true,
  "status": "shared"
}
```

or:

```json
{
  "ok": false,
  "status": "invalid_payload",
  "error": "missing_data_url"
}
```

Android validates the payload, decodes the PNG, writes it under an app cache subdirectory such as `image-shares/`, resolves a `content://` URI through `FileProvider`, and starts:

- `Intent.ACTION_SEND`
- MIME type `image/png`
- `Intent.EXTRA_STREAM`
- `Intent.FLAG_GRANT_READ_URI_PERMISSION`
- `Intent.createChooser(...)`

The existing APK update provider is limited to `apk-updates/`. The manifest and provider paths should be extended or given a separate cache path so image sharing has an explicit `image-shares/` cache location.

## Error Handling

PNG rendering errors continue to use the existing export error path:

`Failed to export response image: ...`

APK-specific failures return structured statuses from Android:

- `unsupported`
- `invalid_payload`
- `invalid_data_url`
- `decode_failed`
- `write_failed`
- `no_share_target`
- `share_failed`

If the sharesheet opens, the operation is considered handed off to the Android system. User cancellation from the sharesheet is not treated as a Web error because Android does not provide a reliable delivery result for arbitrary target apps.

If the sharesheet cannot be opened, Web reports the failure. Android does not save the file to a user-visible location.

## UI Behavior

The response camera button keeps its current placement and icon.

While export/share is in progress:

- the response camera button is disabled or marked busy;
- duplicate clicks should not create multiple PNGs;
- duplicate Android sharesheets should not open.

The chat composer `Photo` button remains an attachment action and is not affected.

## Testing

### Web Unit Tests

Add tests for the response image output service:

- PWA/Desktop calls `downloadBlobAsFile`.
- Android with `shareResponseImage` calls the bridge with a PNG data URL and file name.
- Android without `shareResponseImage` returns an update-required failure.
- Android bridge failure returns a Web-visible failure.

### Web UI Structure Tests

Extend the existing chat UI tests to confirm:

- the completed response camera button remains wired to response image export;
- the chat composer `Photo` action remains an attachment action;
- export/share busy state disables or marks the camera button.

### Android JVM Tests

Add or extend Android tests to confirm:

- `WheelMakerBridge` exposes `shareResponseImage(rawJson: String)`;
- `MainActivity` owns and passes an `AndroidImageShareRuntime`;
- manifest provider paths include the image share cache path;
- runtime uses `ACTION_SEND`, `image/png`, `EXTRA_STREAM`, `FLAG_GRANT_READ_URI_PERMISSION`, and `Intent.createChooser`;
- runtime does not use `DownloadManager`, `MediaStore`, or Downloads as a fallback for response image sharing.

### Manual Checks

- APK: click a completed response camera button and verify the Android sharesheet opens with the generated PNG.
- PWA/Desktop: click the same button and verify the PNG downloads.
- Old APK or missing bridge simulation: verify the Web UI shows an update-required error instead of trying blob download.

## Non-Goals

- No changes to image attachment from the composer.
- No full WebView or screen capture.
- No text attribution or extra body text in the share payload.
- No saving to Downloads, Photos, or MediaStore.
- No chunked bridge protocol in the first version.

If response PNGs become large enough to hit Android JavaScript bridge limits, a future version can replace the single data URL call with a chunked transfer protocol.
